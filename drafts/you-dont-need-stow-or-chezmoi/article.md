# You Don't Need Stow or Chezmoi

It's 2026. We have AI. So here's my advice if you're about to reach for chezmoi, or stow, or any dotfiles manager built for a hypothetical general user: don't. Build your own. This is the era of bespoke software.

I didn't arrive at that opinion in the abstract. My setup runs across five machines split between two employers I don't want bleeding into each other, a VPS carrying its own personal-only data, and a Windows/WSL boundary that can't just symlink across. That's not a shape any general-purpose tool was built for — it's not one config to distribute everywhere, it's several different constraints layered on top of each other, on the same machine, sometimes on the same file.

The setup didn't start ambitious. The first version was a bare git repo living at `~`, configured to ignore untracked files so it would never nag me about anything I hadn't explicitly added. I dropped in the zshrc and configs I actually cared about and ran that same repo, unmodified, on every machine. That worked — right up until I started contracting on the side, on top of a full-time job, and "the same files everywhere" turned out to be exactly the wrong goal. Some things needed to live on one machine and specifically not the other.

The fossil record of that shift is a single commit from 2023-11-23: "move things to new repo and use symbolic links." The tool it introduced was `mklinks.sh` — 52 lines of bash, one function, and a flat hardcoded list of six calls at the bottom: `.zshrc`, `.bashrc`, `nvim`, `fzf`, `starship.toml`, `.gitconfig`. No per-machine awareness. No config file. To add a dotfile, you edited the script. And if a symlink no longer belonged somewhere, nothing removed it — the tool only knew how to add, never to take away.

The worry was never anything dramatic — no trade secrets, no competition. It was mundane: aliases and functions from the contract job showing up on the main-job machine, or vice versa. Probably harmless. But it was surface area, and surface area is a question with no fixed answer: if it's aliases today, what is it tomorrow? Isolation wasn't really a security posture. It was a hedge against a conversation I didn't want to have — keeping what's on my own machine my own business, since no employer is owed an explanation for it.

Worth admitting the limit of that: none of this removes anything from disk. `~/Dotfiles` is cloned in full on every machine — the isolation operates one layer up, in what gets symlinked, sourced, and surfaced, not in what's physically present in the repo. If someone went digging in the working tree itself instead of just using the shell day to day, they'd find everything. What's scoped is the surface, not the source — and the surface is what actually matters day to day. If I'm screen-sharing at Rhyme and type `pr`, I don't want a tool from the contract job popping up in autocomplete with someone asking "hey, what's that?"

There wasn't a single moment things got out of hand — it was accretion, and it never really stopped. More zsh plugins. More function files synced across machines. `mise` entered the picture, and with it a wave of tools — ripgrep, fd, a dozen others — each with its own config file to track. Every new surface tended to spawn its own check right alongside it, from early on — necessary, but still more files. Basic ChatGPT showed up around the same time, and updating all of this stopped being purely manual. Then Claude Code arrived, and the pace changed entirely: symlinks-in-bash became a Python script or two, syncing extended across the Windows boundary — SSH config, an AutoHotkey script — and, for the first time, actual tests started getting written, which was its own new pile of files on top of everything else.

None of this was visible while it was happening. I don't use a file explorer — I live in a terminal, and a terminal only shows you what you ask it to. By the time anyone looked, `home/bin` alone held 110 loose scripts with no substructure at all, and the repo carried 505 tracked files total. Nobody had been browsing. Nobody had been counting. That's the actual shape of sprawl: not a dramatic collapse, just years of accretion nobody was in a position to notice.

The fix wasn't to pile a bigger tool on top of the mess. It was to subtract first. A reorg touched 309 files — almost entirely renames, nothing new added — and gave the sprawl an actual shape: the flat linker module became `install/`, a grab-bag of loose scripts became `orchestrator/` and `tools/`, `systemd/` split cleanly into `services/`. Only once that was done did the real rebuild start: a single unified CLI to replace the pile of scripts, called `dfl`.

That gap from `mklinks.sh` — the tool that could only add, never remove — got closed, but not the way you'd expect. It wasn't that removal was missing and finally got built. It's that an entire category of files had no scoping at all until one commit added it: in June 2026, personal home-automation tooling — Claude Code skills, commands, notes — turned out to be symlinking onto both work machines, indistinguishable from anything else that got installed, because nothing had ever marked it as personal-only. The fix scoped it and tore it down in the same commit. The repo's own instructions to itself put it plainly: a personal skill left over on a work box gets removed, not just skipped.

The constraints from the opening aren't abstract either — each one gets its own sync mechanism, because a single generic "copy this file" can't survive contact with any of them. Windows can't reliably resolve a WSL symlink at login time, so an AutoHotkey script gets mirrored instead of linked. `ssh.exe` reads its own separate credential store outside WSL entirely, so SSH keys get mirrored too — a second mechanism for the same underlying wall, not a redundant one. The VPS has no shared filesystem at all, so everything sent to it goes over a real SSH round-trip. And secrets get rendered through 1Password and pushed separately, since that's a different kind of data than config files. Four mechanisms, four different reasons — none of them scope creep.

Keeping those four mechanisms deliberate doesn't mean new sprawl stopped arriving — it still does, constantly. What's different is what happens after. Nearly every file added in the last year is a check, not a feature, and every single one exists because a problem was first found without one — no exceptions. The clearest example: a backgrounded health check ran with stdin still attached to the terminal instead of detached. The moment it tried to read from it, the kernel sent SIGTTIN and stopped the process cold — for two or three days before anyone noticed. Nobody debugged that in real time. It got noticed, got explained after the fact — root cause and all, in a five-line fix with a docstring that reads like a postmortem — and it will never happen the same way again. That's the actual promise these checks make: not that trouble is anticipated, only that it's never allowed to repeat.

That one wasn't autonomous either — I noticed the check wasn't running and asked why. Claude traced the exact signal chain, we talked through the fix, and it wrote the code. I raised the question. I didn't do the debugging myself. Which is, at this point, how most of `dfl` gets built.

None of this — the teardown, the four sync mechanisms, the checks written one incident at a time — is a recipe anyone else could follow, and that's the point. Most "here's my dotfiles" posts read like a cookiecutter solution: adopt this, your problems go away. They don't, unless you're starting from nothing. Adopting someone else's system means reshaping your own setup to fit it, which is its own friction, not the absence of friction — and it rarely survives contact with the edge cases that are specific to you, because it was never written for you specifically.

It's 2026. We have AI. The advice from the top still holds, but it means something different now than it would have five years ago: don't adopt a tool built for a hypothetical general user when you can just describe your actual constraints and have something built for the constraints you actually have. That's the era of bespoke software. Your dotfiles were never really a one-size-fits-all problem to begin with.
